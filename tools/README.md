# tools

PC에서 USB-CAN 애널라이저로 CAN 프레임을 재생(replay)하는 스크립트를 보관합니다.

PC에는 CAN 포트가 없으므로, 애널라이저가 USB와 CAN 버스 사이를 변환합니다.
NUCLEO는 수신만 하는 리스너이므로 **재생하는 쪽이 없으면 보드 화면에 아무 숫자도 뜨지 않습니다.**

## `replay.py`

Car Hacking Challenge 데이터셋 CSV를 CAN 버스에 순차 재생합니다.

### 보드 실측 테스트 (인자 없이 실행)

```bash
pip install python-can pyserial

python replay.py
```

데이터셋을 이 스크립트와 같은 폴더에 두면(하위 폴더 구조는 그대로 둬도 됩니다)
나머지는 스크립트가 알아서 합니다.

1. CSV를 재귀로 찾아 크기순으로 훑고, 정상만 든 파일과 공격이 든 파일을 하나씩 고릅니다
2. 각 파일의 `Timestamp` 열에서 원본 재생 속도를 계산해 `--rate`로 씁니다
3. 시리얼 포트를 찾습니다. 후보가 하나면 자동 선택, 여러 개면 목록에서 고르게 합니다
4. **1단계** 정상 데이터를 재생하고 화면 판독법을 안내합니다
5. 사진을 찍고 **보드 리셋 버튼을 누르라고** 안내한 뒤 Enter를 기다립니다
6. **2단계** 공격이 가장 몰린 구간을 찾아 그 지점부터 재생합니다

5번의 보드 리셋을 건너뛰면 안 됩니다. min/max 통계는 부팅할 때만 초기화되므로
리셋하지 않으면 1단계와 2단계 측정값이 섞입니다.

### 파일을 직접 지정 (수동)

```bash
python replay.py Pre_train_D_0.csv --port COM7
python replay.py Pre_train_D_1.csv --port COM7 --skip 100000 --limit 50000
```

| 옵션 | 기본값 | 설명 |
|---|---|---|
| `--port` | 자동 탐색 | USB-CAN 어댑터 포트 |
| `--bitrate` | `500000` | CAN 비트레이트 |
| `--baudrate` | `2000000` | 어댑터 시리얼 속도 |
| `--limit` | `20000` | 보낼 프레임 수 (`0`=전부) |
| `--rate` | 원본에서 계산 | 초당 프레임 수 (`0`=제한 없음) |
| `--skip` | `0` | 앞에서 건너뛸 프레임 수 |

`pyserial`은 python-can의 의존성에 들어 있지 않지만 seeedstudio 어댑터에 필요합니다.
빠뜨리면 `the serial module is not installed`로 실패합니다.

포트를 열지 못하면 현재 연결된 시리얼 포트 목록을 대신 출력합니다.

종료 시 실제 달성한 fps를 출력합니다. 목표 속도의 90%에 못 미치면 PC나 어댑터가
병목이라는 뜻이므로 경고를 띄웁니다.

데이터셋은 레포에 포함하지 않습니다. `tools/` 안에 내려받아도 `.gitignore`의 `*.csv`
규칙이 커밋을 막습니다. 폴더 구조는 풀어헤친 그대로 둬도 스크립트가 찾아냅니다.

## 재생 데이터는 실제 트래픽이어야 합니다

같은 ID만 반복해서 보내면 **전처리 시간이 실제보다 훨씬 낮게 측정됩니다.**

`feature_extract.c`의 고유 ID 계산은 이미 센 항목을 건너뛰는 이중 루프라, 윈도우 안의
ID가 몇 종류인지에 따라 작업량이 크게 달라집니다.

| 재생 데이터 | 윈도우당 고유 ID | 내부 루프 실행 |
|---|---|---|
| `Pre_train_D_0.csv` (실제) | 평균 27.4 / 최대 32 | 평균 486회 / 최대 496회 |
| 같은 ID만 반복 | 1 | 31회 |

**16배 차이입니다.** 성능 측정에는 반드시 실제 데이터셋을 재생하세요.

## 재생 속도가 `delta_t`를 결정합니다

**CSV의 `Timestamp` 열은 보드에 전달되지 않습니다.** CAN 프레임에는 시각을 담는
칸이 없어서 ID·DLC·데이터만 버스로 나갑니다. 보드는 도착 시각을 자기 시계로 찍습니다.

```c
/* can_bxcan.c */
frame.timestamp = can_bxcan_now_seconds();
```

즉 `id_delta_t` 특성은 CSV가 아니라 **재생 속도**가 결정합니다. 최대 속도로 쏘면
간격이 실제 주행보다 훨씬 좁아지고, `ID_DELTA_T_LOG_MIN/MAX`로 정규화한 값이 0으로
눌려 학습 때 못 본 분포가 됩니다. 정상 데이터인데도 오탐이 날 수 있습니다.

그래서 `--rate`를 생략하면 원본 `Timestamp`에서 실제 속도를 계산해 씁니다.
`Pre_train_D_0.csv`는 2,402 fps, `Pre_train_D_1.csv`는 2,645 fps입니다.

PC 검증(`ai/notebooks/`)은 CSV의 `Timestamp`를 직접 읽으므로 이 문제가 없습니다.
어긋남은 물리 CAN 버스로 재생할 때만 생깁니다.

`--rate`를 맞춰도 OLED 갱신 중 유실이 나면 그 지점의 간격은 벌어집니다. 따라서
**공격 시 트래픽 폭주로 인한 예산 압박은 이 스크립트로 재현되지 않습니다.**
그것까지 재려면 원본 타임스탬프 간격을 그대로 따라가도록 고쳐야 합니다.

## 파일별 참고

| 파일 | 크기 | 내용 |
|---|---|---|
| `Pre_train_D_0.csv` | 9.3 MB | 179,346프레임, **전부 Normal**, 고유 ID 73종류, `0x043`~`0x5CD` |
| `Pre_train_S_0.csv` | 9.4 MB | 180,686프레임, 전부 Normal |
| `Pre_train_D_1.csv` | 47 MB | 806,390프레임. Flooding 38,521 / Fuzzing 22,620 / Replay 10,509 / Spoofing 988 |

공격이 든 파일은 전부 47 MB 이상입니다. 카톡으로 넘길 만한 9 MB대 두 개는 둘 다
순수 Normal이라, **공격 탐지를 보려면 큰 파일이 필요합니다.**

`Pre_train_D_1.csv`의 첫 공격은 89,574행(11.1% 지점)에 나옵니다. 기본 `--limit 20000`
으로 그냥 돌리면 앞쪽 정상 구간만 재생하고 끝나므로 `--skip`이 필요합니다.
공격이 가장 몰린 구간은 100,000~150,000행(Flooding 15,562행)입니다.

정상 파일을 재생하면 `ATK`는 0으로 유지되는 것이 정상이며, 그 자체가 오탐 관찰이
됩니다. 공격 파일을 재생하면 `ATK`가 0보다 커야 합니다.

## `ATK` 숫자 읽는 법

`ATK`는 공격을 몇 번 잡았는지가 아니라 **경보가 켜져 있던 윈도우 수**입니다.

```c
/* vids_pipeline.c */
if (raw == VIDS_ATTACK) { windows_flagged++; if (s_run < VIDS_K_CONSECUTIVE) s_run++; }
else                    { s_run = 0; }
if (s_run >= VIDS_K_CONSECUTIVE) s_stats.attacks_detected++;
```

`VIDS_K_CONSECUTIVE`가 5이므로 5윈도우 연속으로 걸려야 처음 1이 되고, 이후 계속
걸리는 동안 윈도우마다 1씩 늘어납니다. 공격이 길면 수백까지 올라갑니다.
이 5윈도우 조건이 곧 탐지 지연입니다. 5 × 32 = 160프레임, 2,400 fps에서 약 67 ms.

Flooding은 같은 ID를 도배하는 공격이라 윈도우 안의 고유 ID 종류가 급감합니다.
위의 이중 루프가 짧아지므로 **공격 재생에서 `FEAT`의 min이 더 작아질 수 있습니다.**
버그가 아니라 공격 유형에 따라 전처리 비용이 달라진다는 데이터입니다.
