## 프로젝트 주제

**차량 CAN 버스 침입탐지시스템 (V-IDS)**

차량 내부 통신망(CAN 버스)에 흘러 들어오는 위조된 제어 명령을, MCU에 탑재한 경량 AI로 실시간 탐지하는 시스템.

## 배경 (왜 이 문제인가)

### 1. 거시적 배경 — 왜 지금 더 심각한 문제인가
CAN 버스는 발신자 인증 기능 없이 모든 노드가 메시지를 그대로 신뢰하는 구조다. 이 구조적 결함은 오래전부터 있었지만, 두 가지 흐름 때문에 위험도가 계속 커지고 있다.

- **커넥티드카 확산**: 텔레매틱스·인포테인먼트가 외부 네트워크(셀룰러, Wi-Fi, 블루투스)와 상시 연결되면서, 외부에서 차량 내부망까지 도달할 수 있는 경로(공격 표면)가 늘어남
- **자율주행 발전**: 자율주행 단계가 올라갈수록 사람이 아니라 소프트웨어가 CAN 버스로 브레이크·조향에 직접 명령을 내림. 사람의 개입(마지막 안전장치)이 빠지므로, 같은 위조 공격이라도 사고로 이어질 가능성이 더 커짐

**실제 사례**
- 2015년 지프 체로키 원격 해킹 (찰리 밀러·크리스 발라섹) — 인포테인먼트를 거쳐 CAN 버스에 침투, 원격으로 제동·조향 제어
- 2022~2023년 CAN 인젝션 차량 절도 — 헤드라이트 배선 뒤 CAN 라인에 소형 장치를 꽂아 "정상 인증됨" 신호를 위조, 다수 브랜드 차량에서 실제 피해 발생. 2015년 사례와 동일한 근본 원인(무인증 브로드캐스트)이 최근까지 그대로 악용되고 있다는 증거

**규제**: UN R155(WP.29)는 2021년 1월 발효되었고, EU에서는 2022년 7월부터 신규 형식승인 차량에,
2024년 7월부터는 판매되는 모든 신차에 적용된다. 차량 제조사에 사이버보안 관리체계(CSMS)를
요구하는 이 규제로, 차량 내부 통신 보안은 선택이 아닌 의무가 되었다.

### 2. 기존 방식의 한계
- 규칙 기반 IDS만으로는 **데이터 값을 위조하는 공격**에 대응하기 어렵다. 전송 빈도는 정상과
  같고 내용만 이상하기 때문에, ID마다 정상 값의 범위를 사람이 정의해야 하고 차종·사양이
  바뀔 때마다 다시 정의해야 한다
- 클라우드 기반 분석은 CAN 버스의 밀리초 단위 실시간성을 따라가지 못하고, 통신 두절 시 무력화됨

> 본 시스템은 규칙과 AI를 **역할에 따라 결합**한다. 한 ID가 버스를 점유하는 빈도 기반 공격은
> 경량 규칙이 담당하고, 값을 위조하는 내용 기반 공격은 정상 트래픽을 학습한 오토인코더가
> 담당한다. 규칙을 배제하는 것이 아니라, 규칙이 닿지 않는 영역을 AI가 맡는 설계다.

### 3. 왜 지금 가능해졌는가
최근 몇 년 새 TinyML/경량화 기법이 발전하면서, 이상탐지 모델을 MCU급 하드웨어에 올리는 길이
열렸다. 다만 **모델을 그대로 얹는다고 되는 것은 아니다.** 우리가 쓰는 STM32F103은 부동소수점
연산 하드웨어(FPU)가 없어, 학습된 모델을 그대로 올리면 곱셈 하나하나가 소프트웨어로 처리되어
실시간 예산을 크게 초과한다.

따라서 이 프로젝트의 핵심은 "AI를 얹는 것"이 아니라, **가중치를 정수로 변환하고 연산 경로를
정수 전용으로 재작성해 실시간 예산 안에 밀어 넣는 경량화 과정 그 자체**다.

### 4. 왜 온디바이스(엣지)여야 하는가
브레이크 위조 명령은 밀리초 단위로 판단해야 하는데, 클라우드 왕복 지연이나 터널·지하주차장 같은 통신 두절 구간에서는 근본적으로 대응이 불가능하다.

### 5. 기대효과
차종·사양이 달라져도 정상 주행 데이터만 재학습시키면 재배치 가능한, 실시간·오프라인 동작 가능한 차량용 IDS 참조 구현을 확보.

## 시스템 구조

```
PC (USB CAN Analyzer)              NUCLEO-F103RB (IDS 노드)
정상+공격 프레임 재생   ──CAN 버스──▶  수신 전용 감시 + 온보드 AI 판별
(Challenge 2020 데이터셋)                        │
                                              ▼
                                    이상 감지 시 OLED 표시 + LED/부저 경고
```

- MCU가 1개뿐이므로, PC가 정상/공격 프레임을 재생해 "가상 차량 네트워크" 역할을 하고, NUCLEO는 데이터 프레임을 송신하지 않고 수신만 하는 단일 리스너 구조로 구성
- NUCLEO는 bxCAN **Normal 모드**로 동작한다. 데이터 프레임은 보내지 않지만, CAN 프로토콜상 정상 수신을 알리는 ACK 비트는 낸다. Silent(listen-only) 모드는 2노드 구성에서 ACK를 낼 노드가 없어 성립하지 않음을 보드에서 확인했다(2026-08-24). 실제 차량용 IDS도 ACK를 내는 것이 일반적이다
- 버스에 트래픽을 주입하지 않고 관찰만 하는 방식은 실제 차량용 IDS 제품(탭 방식)과 동일한 아키텍처
- 데이터셋: **Car Hacking: Attack & Defense Challenge 2020** (현대 아반떼 CN7 실차 기반,
  Flooding / Fuzzing / Replay / Spoofing 4종 공격 포함)
- 온보드 모델: **오토인코더 v5** (354차원 입력 → 64 → 16 → 64 → 354). 정상 트래픽만 학습한
  이상탐지 모델로, 가중치를 int8로 양자화하고 연산을 정수 경로로 재작성해 탑재

### 데모 시나리오
1. PC가 정상 차량 통신을 CAN 버스에 재생
2. 중간에 공격 프레임(데이터셋 기반)을 섞어서 재생
3. NUCLEO가 이를 실시간 판별해 이상 감지 시 OLED/부저로 경고

## 향후 계획 — 성능 개선

아래 세 가지는 **측정과 검증을 마쳤으나**, 제출 시점의 검증 사슬을 유지하기 위해
제출본에 반영하지 않았다. 근거 수치를 함께 남긴다.

**1. 컴파일러 최적화 레벨** — 코드 변경 없음

현재 보드 빌드는 CubeIDE Debug 구성(`-O0`)이다. `dense_acc` 안쪽 곱셈 루프가 `-O0`에서
명령어 25개, `-Os`/`-O2`에서 6개다(MAC당 38~50 사이클 vs 12~18 사이클).

| | FEAT | DET | 합계 |
|---|---|---|---|
| 현재 (`-O0`, 실측) | 2.91 ms | 20.30 ms | 23.21 ms |
| `-O2` (사이클 모델 예측) | 약 2.2 ms | 6.5~7.5 ms | **약 9 ms** |

윈도우 예산이 약 11.9 ms이므로 이것만으로 원본 재생 속도를 따라갈 수 있다.
사이클 모델은 실측 DET(20.30~25.04 ms)을 예측 구간(20.6~25.1 ms) 안에서 재현해 검증됐다.
`firmware/Release/`가 `-Os`이지만 `ai_export/`를 빌드 목록에 넣고 있지 않아 정비가 선행돼야 한다.

**2. 출력층 연산 축소** — 재학습 없음

판정에 쓰는 출력 차원만 계산하면 실효 MAC이 윈도우당 32,358 → 18,861로 **41.7% 줄어든다.**
결과가 비트 단위로 동일함을 고정 벡터 1,197개와 난수 20,000개로 확인했다(최대 오차 0).
Flash +84 B, 스택 −8 B.

**3. 판정 파라미터·채점 범위** — 재학습 없음

점수 A의 채점 범위를 354차원 전체 합에서 프레임별 `id_norm` 32칸으로 좁히고,
임계값과 연속 필터를 재설정하면 미사용 평가셋 3종에서 다음과 같이 개선된다.

| | 현재 | 개선안 |
|---|---|---|
| 공격 에피소드 탐지 (78개 중) | 51 | **78** |
| 정상 15.2분 중 헛울림 | 2회 | **0회** |
| AI 단독 탐지 | 16/78 | **36/78** |

Flooding 신호는 `id_norm`이 놓인 32칸에만 있어 354차원으로 합치면 희석된다.
채점 범위를 좁히면 같은 모델로 Flooding 탐지가 0/10에서 10/10이 된다.

## 향후 계획

현재 시스템은 **버스 점유형 공격(Flooding)과 값 위조형 공격(Fuzzing)** 을 대상으로 한다.
반면 **Replay**(과거 정상 프레임을 그대로 재전송)와 **Spoofing**(정상 범위 안에서 값을 미세
변조)은 프레임 하나만 놓고 보면 정상과 구분되지 않아, 현 특성 설계의 범위 밖이다.

이 한계는 확정된 것으로 문서화하되, 해결 경로는 이미 데이터 분석으로 확인해 두었다.

**원인**: 현재 특성은 프레임을 각각 독립적으로 인코딩한다(ID·DLC·데이터 8바이트·재등장 간격).
"직전에 같은 ID가 무엇을 보냈는지"를 보지 않기 때문에, 값이 정상 범위 안에 있으면 구분할
근거가 없다.

**확인된 신호**: 같은 ID의 직전 프레임과 비교하면 두 공격 모두 뚜렷한 차이를 보인다.

| 지표 (같은 ID 기준) | Normal | Spoofing | Replay |
|---|---|---|---|
| 직전 프레임 대비 데이터 변화량 (중앙값) | 25~32 | **0** | **171** |
| 재등장 간격 (중앙값) | 약 10.2 ms | **0.33 ms** | **6.6 ms** |

**적용 방향**: 프레임당 특성에 `직전 대비 데이터 변화량`과 `ID별 기대 주기 대비 편차` 두 개를
추가한다. 이를 위해 ID별 직전 상태를 저장해야 하는데, 현재 ID 테이블은 CAN 표준 ID 전 범위
(2,048칸)를 그대로 잡고 있어 실제 등장 ID(수십 종) 대비 낭비가 크다. **ID→인덱스 매핑으로
테이블을 압축하면 메모리를 오히려 확보하면서 새 특성을 수용할 수 있다.**
